Decision Flow for Four LLM Answers

The strongest workflow treats the project background as standing truth, treats the current question as the local objective, hides model identity during judging, extracts claims into the same shape, then uses two-pass scoring and adversarial review before synthesis.

Is This the Best Process?

This is a stronger process for "borrow strengths and fill gaps" than simple voting because it avoids three common traps: model-name bias, unstructured comparison, and overconfident winner selection.

The remaining weakness is that local HTML scoring is still heuristic. The best version uses the app for structure and traceability, then sends the judge prompt to a real LLM or local model for deeper reasoning.

Recommended Scoring Axes

Axis What It Tests Why It Matters
Project Fit Alignment with loaded instructions and standing context Prevents answers that sound good but violate project reality
Relevance Fit to the current question and constraints Prevents generic advice from winning
First Principles Assumptions, causal logic, tradeoffs, and decision criteria Separates explanation from surface plausibility
Claim Completeness Whether recommendation, assumptions, evidence, actions, and risks are explicit Makes very different answers comparable before scoring
Execution Steps, formats, examples, and verification Turns the decision into something usable
Risk Failure modes, uncertainty, and human escalation points Stops overconfident consolidation
Pass 2 Delta Score movement after consensus, uniqueness, and conflict review Rewards answers that survive comparison, not just isolated scoring

Human Gate Rules

  • Ask the human when the top two answers are within a small score margin.
  • Ask when a decision depends on preference, budget, risk tolerance, or hidden facts.
  • Ask when all four answers agree but none mention the main failure mode.
  • Ask when the project files and the current question pull in different directions.
  • Do not ask when the missing detail can be safely inferred from loaded context.

Built-In Safeguards

Two-Pass Judging

First score each answer independently. Then re-rank after seeing consensus, unique contributions, gaps, and conflicts.

Blind Labels

Hide model names during scoring. Use Answer A, B, C, D until the final report to reduce brand bias.

Claim Extraction

Before scoring, extract each answer's core claims, assumptions, and proposed actions into a common structure.

Adversarial Review

Try to falsify the winning answer before final synthesis. The goal is not negativity; it is decision hygiene.

Evidence Tags

Mark which lines came from project files, the user question, each answer, or the judge's inference.

Memory Update

After the human accepts a final direction, store the reusable principle back into the project background.
